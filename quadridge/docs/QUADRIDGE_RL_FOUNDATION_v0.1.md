# QUADRIDGE 強化学習基盤 設計書 v0.1

## 1. 目的

QUADRIDGEにおいて、将来的に以下を実装するための基盤を構築する。

- ランダムAI
- ヒューリスティックAI
- MCTS
- 自己対戦
- 強化学習
- ニューラルネットワークによる局面評価
- 人間対AI対戦
- AI同士の大量対局によるゲームバランス分析

この段階では、ニューラルネットワークやPyTorchによる本格的な学習そのものは実装対象としない。

まず、

**「UIを起動せず、QUADRIDGEの対局を高速かつ正確に大量実行できる環境」**

を完成させることを目的とする。

---

## 2. 基本方針

ゲームルールを以下から完全に分離する。

- UI
- ブラウザ
- Cloudflare
- WebSocket
- DOM
- アニメーション

ゲームルールの正式な実装を `game-core` に集約し、

- Web版
- オンライン対戦
- AI
- 自動対戦
- 将来の強化学習

から共通利用できる設計とする。

同じルールをWeb版とAI版で別々に実装しない。

## 4. game-coreの条件

`game-core` は純粋なゲームロジックとして実装する。

以下に依存してはならない。

- React
- HTML
- DOM
- CSS
- Canvas
- WebSocket
- Cloudflare API
- Durable Objects
- ブラウザ専用API

Node.js上でもそのまま実行できること。

---

## 5. 盤面

盤面サイズは `15 × 15` とする。

各マスは最低限以下の3状態を持つ。

```ts
type Cell = 0 | 1 | 2;
```

例：

```text
0 = 空き
1 = Player 1
2 = Player 2
```

内部表現は数値でもenumでもよい。

---

## 6. プレイヤー

2人対戦。

```ts
type Player = 1 | 2;
```

勝利方向は以下を基本とする。

```text
Player 1:
上端 ↔ 下端

Player 2:
左端 ↔ 右端
```

方向は将来的に入れ替え可能な設計にしてもよい。

---

## 7. ブロック

使用するブロックは4マスで構成される7種類。

```text
I
O
T
L
J
S
Z
```

内部的には各ブロックを座標配列で表現する。

```ts
type PieceCell = {
  x: number;
  y: number;
};

type PieceType =
  | "I"
  | "O"
  | "T"
  | "L"
  | "J"
  | "S"
  | "Z";
```

各形状について、90度回転した状態を取得可能にする。

---

## 8. 回転

回転は90度単位。

```text
rotation = 0
rotation = 1
rotation = 2
rotation = 3
```

として管理してよい。

UIにおけるQ/E操作はgame-coreでは扱わない。

game-coreでは単純に回転状態だけを扱う。

形状によって同一になる回転状態が存在する場合、合法手列挙時には重複する手を可能な限り除外する。

---

## 9. 3択

各プレイヤーは常に最大3つのブロック候補を持つ。

```ts
type Hand = PieceType[];
```

通常は3個。

自分の手番では、この3候補の中から1つを選択して配置する。

配置後、その枠へ新しいブロックを補充する。

---

## 10. 7種1巡

各プレイヤーは独立したバッグを持つ。

1バッグには以下を1つずつ入れる。

```text
I O T L J S Z
```

バッグ生成時にシャッフルし、順番にドローする。

7個消費後、新しい7種バッグを生成する。

プレイヤー同士でバッグを共有しない。

---

## 11. RNG

AI学習・テストの再現性を確保するため、乱数処理を直接 `Math.random()` に依存させない。

seed指定可能なRNGを用意する。

例：

```ts
reset(seed?: number)
```

同じseedなら、以下を再現できる設計とする。

- バッグ順
- リロール結果
- ランダムAI

---

## 12. GameState

ゲーム全体の状態を1つのオブジェクトで表現する。

```ts
type GamePhase =
  | "normal"
  | "extended"
  | "finished";

interface GameState {
  board: Cell[][];

  currentPlayer: Player;

  hands: {
    1: PieceType[];
    2: PieceType[];
  };

  bags: {
    1: PieceType[];
    2: PieceType[];
  };

  phase: GamePhase;

  turn: number;

  winner:
    | Player
    | "draw"
    | null;

  winType:
    | "connection"
    | "judgement"
    | "draw"
    | null;
}
```

必要に応じてフィールドを追加してよい。

---

## 13. 行動表現

AIが選択する1手を統一形式で表す。

```ts
interface Move {
  handIndex: 0 | 1 | 2;
  rotation: 0 | 1 | 2 | 3;
  x: number;
  y: number;
}
```

`x`, `y` はブロックの基準座標。

基準座標の定義は全形状で統一する。

---

## 14. 合法手列挙

以下の関数を用意する。

```ts
getLegalMoves(): Move[]
```

現在プレイヤーについて、

- 現在の3候補
- 全有効回転
- 全盤面座標

を探索し、合法な配置のみ返す。

AI側で改めて配置可能判定を行わなくてよい状態にする。

---

## 15. 通常配置

通常フェーズでは以下を満たす場合のみ配置可能。

- ブロック全体が盤面内
- 既存の自分ブロックと重ならない
- 相手ブロックと重ならない

つまり通常配置では空きマスのみに配置可能。

---

## 16. 接続判定

自分色のマス同士は、上下左右の辺が接触している場合のみ接続とする。

斜め接触は接続扱いしない。

探索は以下のいずれかで実装可能。

- BFS
- DFS
- Union-Find

---

## 17. 通常勝利

Player 1は `上端 ↔ 下端` が自色の辺接続で繋がった場合に勝利。

Player 2は `左端 ↔ 右端` が繋がった場合に勝利。

ブロック配置直後に必ず勝利判定を行う。

```text
phase = "finished"
winner = 該当Player
winType = "connection"
```

---

## 18. 配置不能時

現在の手札3つについて合法手が0件の場合、そのプレイヤーは配置できない。

ただし、即引き分けにはしない。

7種類の形状から、現在の盤面に少なくとも1つ合法配置が存在する形状を調べる。

配置可能な形状が存在する場合、手札をリロールする。

通常配置中は通常配置条件で配置可能性を判定する。

---

## 19. リロール

配置不能時のリロールでは、盤面に配置可能な形状のみを候補に使用する。

現在配置可能な形状が3種類未満の場合、その形状のみを候補として扱う。

リロール時の7種バッグとの厳密な整合方法について、既存Web実装に仕様が存在する場合はそれを優先する。

存在しない場合は、ゲーム結果に偏りが出にくく、再現可能な方式として実装する。

---

## 20. 手番パス

3択すべて配置不能の場合、

```text
リロール
↓
その手番はパス
↓
相手の手番
```

とする。

同一手番で再配置は行わない。

---

## 21. 延長配置への移行

通常配置ルールおよびリロールを使用しても、両プレイヤーとも通常配置可能な形状が存在しない状態になった場合、ゲームを終了せず `extended` フェーズへ移行する。

延長配置開始時にはブロック候補を改めてドローする。

---

## 22. 延長配置

延長配置では配置条件を変更する。

### 許可

自分の既存ブロックとの重なりを許可する。

### 禁止

- 相手のブロックに1マスでも重なる配置は禁止
- 盤面外は禁止
- 4マスすべてが既存の自分色に重なる配置は禁止

最低1マスは新しい空きマスを獲得する必要がある。

```text
既存自色 3
新規空き 1
→ 合法
```

```text
既存自色 4
新規空き 0
→ 非合法
```

---

## 23. 延長配置中のリロール

延長配置でも3候補すべて配置不能ならリロールを行う。

配置可能形状の検索には延長配置ルールを使用する。

それでもそのプレイヤーが配置できない場合は手番をパスする。

---

## 24. 延長配置中の勝利判定

延長配置であっても通常の勝利条件は変わらない。

自分の担当する対岸を自色マスで辺接続した場合、その時点で勝利。

---

## 25. 勝利可能性

延長配置中、両プレイヤーとも将来的な勝利が不可能と判定できる場合、ゲームを終了可能とする。

勝利可能性判定が高コストになる場合、初期実装では合法手消滅まで進行させてもよい。

ゲーム本体の正式仕様との結果一致を優先する。

---

## 26. 終局時の判定勝ち

通常の接続勝利が発生せず、延長配置でもゲーム終了条件に到達した場合、各プレイヤーの到達度を比較する。

各プレイヤーについて、自色の各連結成分を調べる。

---

## 27. 残り距離

Player 1の場合、

```text
上端までの距離
+
下端までの距離
```

Player 2の場合、

```text
左端までの距離
+
右端までの距離
```

を各連結成分について求める。

最小値をそのプレイヤーの判定値とする。

値が小さい方を判定勝ちとする。

---

## 28. 判定同値

両者の残り距離が同じ場合、以下の順で比較する。

1. 判定対象連結成分のマス数
2. 自色の総占有マス数
3. それでも同値なら引き分け

最終的に、

```text
winner = Player
winType = "judgement"
```

または、

```text
winner = "draw"
winType = "draw"
```

とする。

---

## 29. 判定経路情報

将来Web UIで判定結果を可視化できるよう、判定時には勝者だけでなく、判定対象となった連結成分や距離情報も取得できるようにする。

```ts
interface JudgementResult {
  player1Distance: number;
  player2Distance: number;

  player1Component: Position[];
  player2Component: Position[];

  winner: Player | "draw";
}
```

UI側では以下に利用できる。

- 経路ハイライト
- 対岸までの補助線
- 残り距離

```ts
interface StepResult {

  done: boolean;

    | "connection"
```

## 31. Stateのコピー

AI探索では同一局面から大量の分岐を試すため、`clone()` または `copyState()` 相当の処理を用意する。

MCTSで安全に盤面を複製でき、元の状態を破壊しないこと。

```ts
interface Agent {
```

RandomAgentは `legalMoves` からランダムに1手選択する。

## 36. 異常終了検出

大量対局時に以下を検出する。

- 無限ループ
- 異常に長い対局
- 合法手がないのにstepが要求される
- 不正な盤面状態
- 同一マスを両プレイヤーが所有
- バッグ処理異常

安全策として最大ターン数を設定してもよい。

ただし最大ターン到達を通常のゲーム結果として扱わず、エラーまたは診断対象とする。

## 37. ユニットテスト

最低限以下をテストする。

### ブロック

- 7種類すべて存在する
- 各形状が4マスで構成される
- 回転結果が正しい
- 同一回転形状の重複を必要に応じて除外できる

### 通常配置

- 空きマスへ配置できる
- 自色と重なると配置できない
- 相手色と重なると配置できない
- 盤外へ配置できない

### 延長配置

- 自色との一部重複を許可する
- 相手色との重複を禁止する
- 全4マスが自色と重なる場合は禁止する
- 最低1マスの新規獲得が必要

### 接続

- 上下左右は接続する
- 斜めは接続しない
- Player 1の上下接続勝利を検出できる
- Player 2の左右接続勝利を検出できる

### バッグ

- 7種類が1巡する
- 各プレイヤーでバッグが独立している
- seedによる再現が可能

### リロール

- 3候補すべて配置不能で発生する
- 配置可能形状のみから再抽選される
- リロール後は手番をパスする
- 延長配置でも正しい条件で再ロールされる

### 終局

- 通常勝利
- 延長配置への移行
- 判定勝利
- 完全引き分け
- 判定同値時のタイブレーク

## 41. 対称性

盤面ゲームとして、データ拡張への利用を想定する。

ただしQUADRIDGEは、

- Player 1 = 上下
- Player 2 = 左右

で勝利方向が異なるため、単純な回転や反転ではプレイヤー方向も変換する必要がある。

初期段階では必須実装としない。

将来的に、

- 180度回転
- プレイヤー入れ替え
- 盤面転置

などによる状態変換を検討する。

---

## 42. 性能方針

AI学習では数千〜数百万局を実行する可能性があるため、game-coreでは描画処理を一切行わない。

特に以下を意識する。

- DOM操作禁止
- 不要なdeep copyを減らす
- 合法手探索を効率化する
- 接続判定を過剰に再計算しない
- デバッグログを大量対局時は無効化可能にする

ただし初期実装では、性能よりルールの正確性を優先する。

## 43. GPUについて

この基盤段階ではGPUを使用しない。

以下はCPUで実行する。

- game-core
- RandomAgent
- 合法手探索
- 自動対戦
- 統計取得
- MCTSの初期実装

将来的にPyTorch等によるニューラルネットワーク学習を追加する場合にGPUを利用する。

GPU使用時は、

```python
device = "cuda" if torch.cuda.is_available() else "cpu"
```

のようにCUDA利用可否を自動判定できる構成を想定する。

# Codexへの実装指示
